# Payment recovery — 27 August 2026

## Delivered

Admin → Commerce → Payments now offers **Verify with iKhokha** for authorised staff with order-view and update permissions. The action requires a saved provider reference and configured credentials, confirms its effects, and performs an authenticated read-only provider lookup. It never creates another charge.

Only the documented PAID result with the exact reference and integer minor-unit amount can settle a matching ZAR order. Unknown/failed statuses, mismatches, unavailable providers and stale local records do not infer payment success or failure. A transaction lock and shared settlement prevent duplicate inventory/invoice processing. Cancelled/refunded orders retain their protections. Checks record staff, time, outcome, provider status and amount; raw responses and secrets are not copied into the audit.

Receipt delivery now waits until the outer payment/audit transaction commits. A failed audit write rolls back payment, stock and invoice changes without sending a receipt. Checks are limited to once per minute per transaction and use a short shared lock. Network requests run outside database locks.

The Payments page is private/no-store and requires an administrator role plus order visibility. It shows last verification and setup guidance. Amounts use their recorded currency rather than assuming ZAR for every historical payment.

Payment link creation/resumption accepts only HTTPS links on the documented securepay.ikhokha.red host, without user information, custom ports or fragments. Credential-bearing API calls use the documented API endpoint, disable redirects and have connection/request timeouts. Invalid provider responses produce fixed safe errors. Webhook JSON shape, field types and size are validated before database lookups.

## Still required before launch

Merchant iKhokha Application ID/Secret and real merchant-approved settlement tests remain necessary. This is manual staff recovery, not unattended reconciliation. A payment creation timeout with no saved provider reference still requires merchant-dashboard review. Local hold expiry does not cancel external payment links. Gateway refunds/credit notes, Stripe modernisation, DSV account-specific integration, purchasable variants and complete international/security/load/restore verification remain open.

No refund endpoint was invented. iKhokha documents refunds through its merchant tools; the public API guide inspected here did not provide a refund integration contract. DSV requires the merchant's selected API product/access, service coverage and test credentials before implementation and validation.
